# 兔咪室友互動：第一段劇本與素材路線評估

2026-09-08。這份是本次討論的劇本初稿與技術評估，尚未實作；不是新的全專案規則。
已確認方向與待驗證提案分開標示，後續定案再同步角色指南、對話目錄及素材規格。

## 使用者已確認的方向

- 兔咪可自行命名；牠為了進步離開家人，想試著獨立生活、培養好習慣。
- 使用者搬進兔咪的新家，關係是室友，兩人一起培養習慣、一起進步。
- 性格天真、善良，重視生活中的小反應。使用者以吉伊、小八的特質作為溝通參考。
- 兔咪的實際聲音沿用目前 MI 語音，由介面字幕讓使用者理解意思。
  使用者以邦布的發聲與翻譯關係為例；不導入其他作品的聲音、台詞或角色素材。
- 正式頁的特定事件：上方兔咪演出，下方功能區切換成可回應的選項。
- 前導與正式頁分別設計；外觀、沉浸感、動畫與音效是重要產品目標。

## MI 聲音與字幕的分工（呈現建議，待試看）

兔咪發出 MI 聲；字幕是那段表達的意思，可以是完整短句。
「少語」描述的是聲音與演出密度，不代表使用者只能猜動作，也不限制翻譯只能有兩個字。
不需要逐中文字生成或拼接一個 MI，不做嘴型動畫。

建議主字幕直接呈現意思，聲音由音訊承擔，例如：

> 聽到：短短、上揚的 MI 聲。
>
> 字幕：你就是新室友嗎？

使用者提出的 `Mi？（你就是新室友嗎？）` 也可成立。
建議先採「意思作主字幕」：日常不重複印出發聲，第一次相遇以一句介面提示
「兔咪用 MI 聲說話，字幕會傳達牠的意思。」建立約定。
若試看後希望保留發聲文字，可用小一級的 `Mi？` 加同區域主字幕，避免擬聲字搶走選項閱讀空間。
括號內的意思是兔咪的表達；動作旁白（例如「牠挪開了箱子」）另用敘事文字，不能混成兔咪說的話。

現有素材在 [SfxCue](../lib/utils/sfx_service.dart)：
`tumiConfirm`、`tumiQuestion`、`tumiHappy`、`tumiCheer`、`tumiSad`。
以下劇本只提出語意配對，未試聽混音或量測播放延遲；實際節奏仍需以音檔與畫面校準。

- 每句依情緒挑一段現有聲音；等待回答時保留安靜，不反覆呼叫使用者。
- 聲音不承擔唯一資訊；靜音也能完整看懂。字幕讀屏讀意思，不逐字唸 MI。
- 點一下補全正在出現的字幕，完成後再點才前進；選項保持可讀，無倒數。
- 語音開始時呈現字幕，不要求字幕字數等於聲音長度；讀完時間由使用者掌握。
- 降低動態效果仍保留字幕、選項、表情與分支結果。

現有五種聲音可先驗證方向，但長對話可能暴露重複感。待劇本試聽後，再決定是否補充
同一聲線的短／中句、猶豫與輕聲招呼等錄音；不靠大幅變速變調把五段硬湊成整套語言。

## 前導第一幕：搬家第一天（劇本初稿）

目的：讓使用者理解兔咪的語言、室友關係，並親自完成一次有差別的回應。
本幕不承擔所有前導設定；命名、習慣和功能啟用在後續步驟銜接，原有資料不在此改寫。
場景提案為新家玄關與桌邊，現有前導背景和道具尚未滿足這段演出。

| 拍點 | 畫面與動作 | MI 語音／意思字幕 | 下方互動 |
|---|---|---|---|
| 抵達 | 門內有輕微紙箱摩擦聲，稍停後兔咪探出頭 | 暫時無語音、無意思字幕 | 「輕輕打招呼」；第一個操作建立參與感 |
| 察覺 | 兔咪看看使用者方向，再看看行李 | `tumiQuestion`；「你就是新室友嗎？」 | 「嗯，今天搬進來。」 |
| 邀請 | 兔咪向屋內示意，發現箱子擋著門 | `tumiConfirm`；「先進來，這裡還沒整理好。」 | 點擊繼續 |
| 小插曲 | 兔咪抱住箱子，挪了一點又停下，抬頭看你 | 無台詞；由動作交代狀況 | A「扶住箱子的另一邊」／B「先把自己的行李移開」 |
| A 回應 | 箱子被穩穩挪到旁邊，兔咪鬆開手、抬頭笑一下 | `tumiHappy`；「一起搬，好多了。」 | 點擊繼續 |
| B 回應 | 通道空出，兔咪改從側面推過去，再向你點頭 | `tumiConfirm`；「這樣就過得去了。」 | 點擊繼續 |
| 匯合 | 畫面轉到桌邊，有兩個杯子，兔咪把其中一個推向你 | `tumiConfirm`；「這個留給你。」 | 「把杯子放在一起」 |
| 約定 | 桌上的小本子露出一張起床的小圖，兔咪指指自己 | `tumiConfirm`；「明天想早一點起來。」 | 「我也有想開始的小事。」／「先一起把家安頓好。」 |
| 收尾 | 兔咪點頭，兩個杯子留在同一畫面，音樂自然延續 | `tumiHappy`；「Mi」的短聲，意思字幕「嗯，一起。」 | 接到後續認識與設定流程 |

分支的差別是合作方式與兔咪的具體反應，不設隱藏的好／壞答案或加減好感。
「家人的小毯子」「寄來的點心」「回憶本成為日記」是後續故事候選，本幕不堆入所有身世。
使用者給兔咪的新叫法如何與原名共存，留在命名幕討論，不讓本幕先決定。

### 正式頁的短事件接續示例：杯子的位置

兔咪整理桌面，把兩個杯子放好，看看你的方向。
播放 `tumiQuestion`，字幕「杯子放這裡，好嗎？」
使用者選「並排放就好」或「我的放靠門這邊」。兔咪依選擇移動杯子，
播放一次 `tumiConfirm`，字幕「嗯，記住了。」然後回到原功能頁。

只有確實保存選擇且後續事件有讀取時，才能使用「記住了」。原型若只有本次分支，
字幕先用「嗯，就放這裡。」。這是可驗證的連續性，不宣稱角色具有尚未實作的記憶。

## 事件系統需要承擔的事情

先確認劇本再決定程式介面。預期把事件進度、選項與演出，從各功能頁分離：

- 事件持有進度：進場 → 說話 → 等待選擇 → 分支反應 → 收尾／暫停。
- 角色顯示同時表達姿勢、表情與語音，不把每句字幕都新增成一個情緒 enum。
- 使用穩定的事件／節點／選項 ID；素材與字幕文字可替換，選擇結果不可靠字串識別。
- 功能面板保留原 state、捲動與輸入；背景計時照常，重要計時提示可暫停事件。
- 一般事件先等待輸入或重要操作結束；提供稍後再聊，退出不扣分。
- 對話擁有角色演出的期間，既有十秒收尾、其他頁反應和閒置暫停不能清掉等待中的對話。
- 連點只提交一次。保存失敗可重試；離開／回前景先核對節點，避免重播獎勵或重套選擇。
- 事件若跨換日恢復，重新核對條件與功能資料；昨天的事不能套用成今天已完成。
- 前導和正式頁共用對話能力，但觸發、退出與設定完成條件各自定義。

正式反應開始實作前，先更新 [對話目錄](tumi_dialogue_catalog.md) 的事件總表，
依 [UI／Motion 流程](ui_motion_protocol.md) 驗證真實布局與模擬器畫面，並跑相關測試。

## 素材現況與成本來源

2026-09-08 檢查：`assets/mascot/core/` 有 12 個正式情緒 PNG 與 1 張中性眨眼差分。
目前只有 core 造型。`skinnedMascotAsset` 在
[wardrobe_catalog.dart](../lib/utils/wardrobe_catalog.dart) 做同名路徑替換；
[造型完整性測試](../test/wardrobe_skin_assets_test.dart) 要求每套覆蓋 core 圖組。

整張圖含角色毛髮、衣物遮擋與明暗。把一張衣服 PNG 貼在上面，只能處理有限的固定姿勢；
轉身、抬手、衣服在手臂後方、耳朵壓住帽子等，需要對應形狀、前後層次及陰影。
獨立繪製正面與背面也不會自動得到轉身的中間幀。

例如每套 30 張、10 套，共有 300 個完整圖輸出需要檢查（純示例，不是開發目標）。
AI 可以協助設計造型與局部差分，不能把「生成一張衣服」視為「已驗證全部姿勢」。
製作時需分辨衣服紋理變化與改變輪廓的服裝：圍巾、帽子、外套的適配成本不同。

## 技術路線比較（工程判斷，未做樣品實測）

| 路線 | 重用方式 | 需要投入的工作 | 對兔咪的適用判斷 |
|---|---|---|---|
| 整張 CG 差分＋Flutter 演出 | 既有畫面與演出可沿用，造型逐張輸出 | 每個姿勢／造型的一致性與接續檢查 | 第一段互動原型最直接；大量動作與造型時製作量上升 |
| 固定姿勢分層配件 | 共用身體，衣服／道具透過錨點與遮罩組合 | 各姿勢的配件形狀、前後層次、接觸陰影 | 頭飾、小配件可試；不能推論所有服裝都自然貼合 |
| 2D 網格／骨架，例如 Live2D、Spine | 部件變形與動畫重用，造型替換對應部件 | 拆圖補畫、網格／綁定、換裝校正、轉角素材、Flutter 整合 | 正面演出值得測；大角度轉身要額外設計，CG 毛邊與陰影需專門驗證 |
| 3D 母模型＋預先渲染 | 在製作端共用模型、骨架、相機與動作，再逐套輸出圖片／短動畫 | 核准外觀重建、材質燈光、服裝建模與權重、渲染與播放驗證 | 若多角度、動作與換裝成為核心，優先做小樣評估；App 可繼續使用 2D 呈現 |
| 即時 3D | 執行時共用骨架與模型，服裝跟著變形 | 上述製作成本，加上渲染整合、透明混合、裝置效能與外觀一致性 | 確定需要連續自由轉向／即時姿態後再考慮，不是本次已選方案 |

Live2D 官方要求素材拆分，並補畫部件移開後會露出的區域；
Spine 的 skins 支援讓骨架動畫重用於不同附件集合。[1][2]
這些能力建立在已製作好的部件和綁定上，不等同單張成品圖自動變成可動角色。

Blender 可將動畫輸出為影格序列。[3] 因此「在製作端用 3D」和「App 採即時 3D」
可以分開決定。預渲染仍會增加最終圖片／影格數量，只是把逐張重畫改為可重跑的輸出；
須另外驗證透明邊緣、包體、解碼記憶體與幀率，不能假定必然更省電。
服裝綁定也可能需要人工修權重，不能承諾任意 AI 服裝素材都會自動適配。[4]

目前 pubspec 沒有導入 Live2D／Spine／即時 3D runtime；本次未做 Flutter SDK 整合、
授權價格、建模報價或 iPhone 效能測試。選定候選工具時再查當時官方整合與授權條件。

## 建議的投資順序

1. **用本幕確定互動語言。** 先確認 MI＋字幕、兩條分支、等待與收尾是否有室友感。
   劇本試看只用現有素材標示情緒時，必須註明探頭／搬箱子等動作尚未被驗證。
2. **建立小份角色設定圖。** 以核准正面圖為身份標準，核准側面、背面與比例；
   這些是模型／差分的設計依據，不是先量產所有角度的所有表情。
3. **做一組能揭露問題的素材樣品。** 同一套代表性衣服，涵蓋正面、側面／背面、
   抬手及耳朵遮擋；比較身份一致性、衣物接觸、轉身連續性與每次修正成本。
   先選要測的服裝與路線，不同時製作全部候選技術。
4. **通過樣品後才擴充日常動作。** 以事件需求決定察覺、聆聽、思考、遞物、放鬆等動作。
   每個動作有可接回待機的起止姿勢。完整動作庫大小由實際內容決定。

暫定建議：近期沿用 CG 完成互動驗證；若多角度與換裝需求確定，下一個技術樣品
優先考慮 3D 母模型＋預渲染。能否忠實重現核准兔咪，是決定採用前的首要關卡。
這是條件式建議，尚未啟動建模、生成新兔咪／造型或更換技術。
